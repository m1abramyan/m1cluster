# Настройка включения с двигателем и запуск приложения

Статус: локальный аудит и подготовка упаковки, 14 ноября 2026 года. Текущий кандидат выпуска — **0.3.1 / `manually`**. Автозапуск не входит в этот ручной выпуск и не активирован. В рамках этого аудита подключений к автомобилю, установки, изменения provisioning и перезапуска MGU не выполнялось. Сообщение владельца об установленной версии 0.3.0 зафиксировано отдельно в [FIRST_CAR_FEEDBACK_2026-11-14.md](FIRST_CAR_FEEDBACK_2026-11-14.md); оно не подтверждает автозапуск, восстановление штатной приборки или видимость предупреждений.

## Два независимых механизма

1. **Запуск процесса приложения** выполняет менеджер MGU. До запуска процесса наша конфигурация и обработчик двигателя не исполняются.
2. **Включение отрисовки** выполняет уже работающий `RetroRuntime`, когда пользователь разрешил отображение и доступны необходимые источники и renderer. Открытие страницы настроек не требуется.

Настройка «включать при запуске двигателя» в пакете `manually` способна управлять только вторым механизмом. Она не может сама запустить завершённый процесс после сна/перезагрузки или заставить менеджер удерживать его в фоне. Сохранённый флаг не является регистрацией системного автозапуска.

## Почему Waze появляется автоматически

В [пакете Waze OAP 0.6.8](https://github.com/robertnisipeanu/idrive-apps/blob/f7a678b27693c88a12d2ed4f18ac4652f005bffd/apps/robertn_waze_cluster/package/package.json) **нет** `mguAppStartType`. Его [RHMI application.json](https://github.com/robertnisipeanu/idrive-apps/blob/f7a678b27693c88a12d2ed4f18ac4652f005bffd/apps/robertn_waze_cluster/package/rhmiData/application.json) содержит обычную точку входа настроек, а не специальный projection-autostart атрибут. `oapAppSettings.visibility: FOREGROUND` само по себе не является командой открыть страницу.

Автоматическую карту обеспечивает отдельный native tool: [waze-on-cluster 0.9.14, component.json](https://github.com/robertnisipeanu/idrive-apps/blob/f7a678b27693c88a12d2ed4f18ac4652f005bffd/native/waze-on-cluster/component.json) устанавливает и включает службы; [waze-on-cluster.service:45–54](https://github.com/robertnisipeanu/idrive-apps/blob/f7a678b27693c88a12d2ed4f18ac4652f005bffd/native/waze-on-cluster/systemd/waze-on-cluster.service#L45) запускает процесс с `multi-user.target`, а socket также может активировать службу. Там есть отдельные capture/projection patches, boot recovery и `Restart=on-failure`; это не механизм нашего приложения.

В OAP-коде [_appInitialized / _startedForeground:161–196](https://github.com/robertnisipeanu/idrive-apps/blob/f7a678b27693c88a12d2ed4f18ac4652f005bffd/apps/robertn_waze_cluster/src/robertn_waze_cluster.js#L161) отделены запуск без RHMI и причины открытия UI; [_onEntryPointExecute:384–396](https://github.com/robertnisipeanu/idrive-apps/blob/f7a678b27693c88a12d2ed4f18ac4652f005bffd/apps/robertn_waze_cluster/src/robertn_waze_cluster.js#L384) открывает страницу по точке входа. Кнопки [enableMap/disableMap:353–364](https://github.com/robertnisipeanu/idrive-apps/blob/f7a678b27693c88a12d2ed4f18ac4652f005bffd/apps/robertn_waze_cluster/src/waze_cluster_control.js#L353) отправляют apply/revert демону патчей. Такие операции, службы и зависимости **не переносятся** в Retro Cluster: для нашего существующего фонового кода используется поддерживаемая Store политика запуска OAP-приложения.

## Есть ли API смены системного автозапуска из приложения

В изученном публичном runtime, UI MGU Store, протоколе его updater и deploy-коде **не найден подтверждённый API**, позволяющий нашему приложению переключить свой `appStartType` после установки. Найденный рабочий путь — обычное install/update с соответствующим полем пакета. Не следует придумывать метод SDK или обращаться к приватному протоколу, редактировать системный `custom_apps.json` напрямую либо выдавать изменение нашего JSON за изменение start type.

В Store tests `deploy/test/run.js:673–681` предусмотрен переход manual → autostart через обновление и обратно через следующее обновление. Эти исходники прочитаны; полный upstream test suite и аппаратная проверка не запускались. `lum` — допустимое значение пакета, но отдельной подтверждённой привязки этого режима к запуску двигателя в данном аудите нет.

## Варианты для четырёх настроек iDrive

Общие настройки: разрешение отображения, включение с двигателем, язык RU/EN, независимые единицы скорости, температуры, давления и расхода. Реализован вариант A; вариант B объясняет отдельную системную политику, которую этот переключатель не меняет.

### Вариант A: включение отрисовки внутри работающего процесса

Текущая подпись — **«Включать при запуске двигателя»**. В manual-пакете рядом указано: «После выключения автомобиля нужен ручной запуск приложения». В подготовленном auto-варианте пояснение сообщает об автоматическом запуске процесса и о возможности выключить отображение главным переключателем. Вариант текста берётся из фактического `ctx.spec.mguAppStartType`, а не из пользовательского файла. Опция `startup.onEngineStart` по умолчанию выключена. Главный переключатель отображения имеет приоритет: его выключение немедленно освобождает слои и не отменяется следующим событием двигателя.

Реализованное поведение:

- При выключенной опции — обычное ручное разрешение отрисовки с существующими проверками источников.
- При включённой опции — ожидать прямую достоверную запись `engineRunning === 'running'` и активное состояние автомобиля. `starting`, неизвестный код, RPM >0, температура или FES не являются заменой.
- Первое `running` после ручного запуска приложения может быть начальным getter-снимком уже работающего двигателя. Это достаточное условие для разрешения отрисовки, но не доказательство нового физического запуска двигателя.
- После подтверждения сохранять разрешение только в оперативной памяти текущей активной сессии. Обычная остановка двигателя системой start-stop не должна внезапно скрывать приборку. Завершение активной сессии/сон, потеря соответствующего поколения источника и ручное выключение сбрасывают разрешение; при новом запуске процесса оно не восстанавливается из файла.
- Недоступные скорость/передача и другие действующие критические условия по-прежнему освобождают слои. Новое `running` не обходит отказ renderer, проверку безопасности и ограничение повторного запуска.

Дополнительные таймеры, диагностический опрос, запись в блоки и удержание автомобиля активным не нужны. `signals.watch` уже делает начальный getter при наличии его описания и получает уведомления; источник запрашивает свежие снимки после смены активной сессии. Повторные одинаковые события не должны создавать новую сцену или подписки. Точное поведение start-stop и доставки событий после сна требует проверки на автомобиле.

### Вариант B: именно системный автозапуск процесса

Отдельного checkbox системного автозапуска в интерфейсе нет. Существующая опция двигателя управляет отрисовкой и не меняет `mguAppStartType`. Для системного запуска требуется версия с соответствующей политикой пакета. После отдельной проверки ручного запуска, выключения и восстановления штатной приборки можно подготовить новую версию с `mguAppStartType: autostart`, установить её отдельным разрешённым шагом и проверить lifecycle на машине. Этот документ не выполняет такой шаг.

Даже в autostart-пакете выключатель отображения должен оставлять процесс спокойно работающим без слоёв, а не вызывать `exit`: менеджер может вновь запускать его. Системная политика и ожидание двигателя остаются независимыми. Переход обратно к `manually` подтверждён через следующее обновление пакета, не через локальный runtime-checkbox.

## Ручной выпуск 0.3.1 и подготовка будущего автозапуска

Сейчас `apps/manuk_retro_cluster/app.json` содержит `version: 0.3.1`, `mguAppStartType: manually`; конфигурация и сохранённые `enabled`/`startup.onEngineStart` не переключаются. Автоматический режим не опубликован и на автомобиль не устанавливался.

После отдельного подтверждения ручного выключения, возврата штатного изображения и видимости предупреждений согласованный будущий auto-выпуск может установить в `app.json` версию 0.3.2 и `mguAppStartType: autostart`. Существующий Store source flow `mgu-repo.json → tools/build.py {id}` теперь сохранит эту объявленную политику в итоговом пакете. Само наличие строки в исходнике больше не расходится с принудительным manual override сборщика. Нужен реальный SDK/Store donor; локального реального SDK по-прежнему нет.

Для явной сборки будущего auto-обновления относительно текущего исходного manual-выпуска 0.3.1 существует команда:

```sh
python3 tools/build.py manuk_retro_cluster --autostart-after-manual-test --version 0.3.2
```

Флаг требует версию строго новее текущего `app.json`. Если будущий исходный выпуск будет объявлен как 0.3.2/autostart, обычная Store-сборка выполняется без этого флага. Обратный явный выбор ручного запуска в следующем выпуске 0.3.3 поддерживает команда:

```sh
python3 tools/build.py manuk_retro_cluster --manual-start --version 0.3.3
```

Это команды **сборки**, не установки или перезапуска. При отсутствии реального SDK они отказываются выпускать автомобильный пакет. Auto- и manual-override нельзя передавать одновременно. Для опубликованного ручного source-выпуска его собственный `app.json` также должен объявлять `manually`; никакие системные файлы через приложение не редактируются.

Итоговая проверка должна читать `package/package.json` из полученного `.tgz`: наш id, согласованную версию, `mguAppStartType: autostart` или `manually`, отсутствие `mguBenchOnly` и SDK-заглушки. `javascript/kit/app-spec.json` должен содержать тот же фактический тип. `manifest.json` сохраняет прежние read/subscribe сигналы, без новых методов записи или диагностических разрешений. На автомобиле выключение отображения сохраняется в прежнем `data/manuk_retro_cluster.json`; обновление не должно заменять этот файл значениями по умолчанию.

## Границы дальнейшей реализации и проверки

Не сохранять `engineRunning`, событие запуска или разрешение текущей сессии как состояние следующего запуска. Не включать автоматически `enabled`, если пользователь явно выключил отображение. Не создавать daemon/watchdog, restart loop или автоматическое открытие настроек на центральном экране. Автозапуск испытывают после подтверждённого ручного выключения и проверки штатных предупреждений. Ошибка сохранения при выключении освобождает слои и останавливает runtime; сохранение выключенного состояния после такой ошибки нельзя обещать до исправления записи.

Автоматически проверены `tests/engine-start.test.js`: неизвестное/starting/running состояние, начальный снимок уже запущенного двигателя, повторные события, start-stop в одной сессии, потеря CDS, сон/пробуждение, ручное выключение, потеря критических данных и перезапуск с сохранённой **настройкой**, но без сохранённого автомобильного состояния. Проверки используют настоящий `RetroSource` и `RetroRuntime` с подставленным renderer, не автомобиль. Подписки не дублируются; новых таймеров или опросов для этой опции нет.

`tests/config-migration.test.js` и `tests/display-settings.test.js` проверяют перенос версий 1–6 в схему 7, удаление настройки виджета, сохранение прочих параметров, 16 комбинаций независимых единиц, строгий тип новой опции и атомарное сохранение. Некорректный файл и безопасное выключение проверяются `tests/config.test.js`. Статическая проверка совместимости ES2017/API выполнена; она не является запуском на Node 8.

При подготовке упаковки выполнены 16 тестов `tests/build_test.py`: исходный manual-пакет; изолированная **bench-only** копия с историческими тестовыми номерами source0.3.0 → 0.3.1/autostart; совпадение типа в package/runtime spec; обратный manual override; маршрутизация настоящего source CLI; отклонение несовместимых флагов/неизвестного типа; отказ без SDK или с SDK-заглушкой для default/auto/manual. Эти номера fixture не задают политику текущего выпуска: настоящий кандидат 0.3.1 остаётся ручным, будущий auto-вариант — 0.3.2. Ни один этот тест не создаёт устанавливаемый `.tgz`/`.mgu`. `tests/settings-ui.test.js` проверяет manual/auto пояснения RU/EN без открытия страницы и без изменения главного разрешения; `tests/runtime-background.test.js` запускает реальный `mgu.run` с подставленным SDK без RHMI и проверяет корректное завершение по `shutdown`. Эти тесты повторно прошли 14 ноября; автомобильную совместимость они не доказывают.

## Отдельный критерий: открытие настроек после фонового запуска

При `app.rhmiApplication === null` код `kit/runtime/mgu.js:524–527` возвращает фон до регистрации обработчика открытия страницы. Локальная проверка подтверждает начальный фон, но не доказывает, как конкретный SDK/менеджер на G30 предоставит RHMI при последующем нажатии плитки. Это существенно для доступности выключателя, а не только удобства меню.

Auto-пакет пока не активируется и не публикуется: сначала нужны ответы владельца о штатных предупреждениях и ручном выключении, затем согласованный безопасный способ проверки открытия настроек из фона. Текущие сообщения владельца — в [FIRST_CAR_FEEDBACK_2026-11-14.md](FIRST_CAR_FEEDBACK_2026-11-14.md).

Для разрешённого испытания на стоящем автомобиле критерии проверяются раздельно:

1. Процесс запускается без ручного открытия приложения, настройки не перекрывают штатный экран.
2. После фонового запуска нажатие плитки открывает реальные настройки; доступен главный выключатель отображения.
3. Выключение освобождает собственные слои; владелец видит штатную приборку и предупреждения.
4. После следующего обычного цикла сна/запуска сохранённое выключение не отменяется.

Пока пункт 2 не подтверждён, доступность штатного UI-выключателя после auto-старта не считается доказанной. Непроверенный lazy-init API SDK для этого не добавляется; большой рефакторинг `mgu.js` без данных о реальном SDK не выполняется.

На G30 отдельно проверить доставку `statusEngineStatus`, поведение start-stop и сна, завершение manual-процесса менеджером и реальное поведение autostart только после разрешённой установки соответствующей версии.
